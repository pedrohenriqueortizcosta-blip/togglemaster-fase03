Intro

02

Infrastructure as Code

3:30
Show
  • The terraform/ folder structure — root config + modules/ (networking, eks, rds, elasticache, dynamodb, sqs, ecr, irsa, github-oidc).
  • terraform plan running against the live state.
  • AWS Console: VPC → EKS cluster togglemaster → the 3 RDS instances → ElastiCache → DynamoDB table → SQS queue → the 5 ECR repos.
terminal

cd terraform
terraform plan
The point of this moment: plan reports 0 to add, 0 to change, 0 to destroy — proof the entire AWS environment on screen was produced by this code, not console clicks, and nothing has drifted since.
Say
  • "Every module is separate and reusable — networking, EKS, and one RDS module instantiated three times via for_each for the three Postgres databases."
  • "State isn't local — it's a versioned, encrypted S3 backend with native locking, itself provisioned by a small separate bootstrap config, so its lifecycle is decoupled from the environment it stores."
  • "This is a personal AWS account, so Terraform creates its own IAM roles — the EKS cluster role, node role, and two IRSA roles that let evaluation-service and analytics-service reach SQS and DynamoDB with zero static AWS keys anywhere."
  • "terraform plan reporting zero changes is the real proof this matches what's live — that's everything you're about to see in the console."
03

Pipeline anatomy

1:30
Show
  • Open .github/workflows/flag-service-ci.yml on GitHub, and a past successful run's job graph on the Actions tab.
✓ Build & Unit Test ✓ Linter ✓ Security Scan ✓ Docker Build & Push ✓ Update GitOps manifest
Say
  • "Five jobs, every push to main and every pull request: build & unit test, lint, a security scan, Docker build and push, and a GitOps update — the last two only run on a push to main, not on PRs."
  • "Security scan does two things — SCA with Trivy against the dependency manifest, and SAST with gosec or bandit depending on the language. Either one failing on a CRITICAL finding stops the pipeline before it ever builds an image."
  • "Pushing to ECR uses GitHub's OIDC token to assume an AWS role directly — no access key sitting in a GitHub secret."
04

DevSecOps: fail, then fix

4:30 the required beat
Show
  • Editor: open flag-service/requirements.txt, add one line, save.
  • Terminal: commit and push.
  • GitHub Actions: the security-scan job turning red, with the Trivy table visible in the log.
flag-service/requirements.txt — add this line

PyYAML==5.3
terminal

git add flag-service/requirements.txt
git commit -m "test: add vulnerable dependency"
git push
What Trivy actually reports — verified locally before recording, so this is guaranteed to reproduce on camera:
LibraryCVESeverityFixed inIssue
PyYAMLCVE-2020-14343CRITICAL5.4incomplete fix for CVE-2020-1747
PyYAMLCVE-2020-1747CRITICAL5.3.1arbitrary command execution via FullLoader
Say (while it's red)
  • "I'm adding a real, known-vulnerable package version — PyYAML 5.3 has two CRITICAL CVEs for arbitrary code execution. It's not even imported anywhere in the code; Trivy scans the dependency manifest itself, which is exactly the point of SCA scanning."
  • "The pipeline fails right here, at security-scan — it never reaches Docker build, never reaches ECR, never reaches the cluster. That's the blocking rule the challenge asks for."
Show
  • Editor: delete the PyYAML==5.3 line, save.
  • Terminal: commit and push again.
  • GitHub Actions: the same job turning green.
terminal

git add flag-service/requirements.txt
git commit -m "fix: remove vulnerable dependency"
git push
Say (while it's green)
  • "Same commit shape, one line removed — security-scan passes, and now the full chain runs: Docker build, a container image scan, push to ECR, and the GitOps update job. Let it keep running — that's Segment 5."
05

GitOps: the tag update

3:30
Show
  • GitHub Actions: the update-gitops job's log — the sed step, then the commit/push step.
  • GitHub: the repo's commit history — a new commit authored by github-actions[bot].
  • The diff on gitops/flag-service/deployment.yaml: the image: line's tag changing to the new commit hash.
terminal — after the push, once CI finishes

git log --oneline -5 -- gitops/flag-service/deployment.yaml
git pull
git diff HEAD~1 -- gitops/flag-service/deployment.yaml
Say
  • "CI never runs kubectl apply itself. Its last job edits exactly one line — the image tag — in gitops/flag-service/deployment.yaml, and commits that change back to this same repo using the workflow's own token."
  • "That commit is the entire interface between CI and CD. Nothing downstream needs pipeline access to the cluster at all."
06

ArgoCD: the sync

3:30
Show
  • The ArgoCD UI: the flag-service tile flipping from Synced to OutOfSync to Syncing and back to Synced — usually within its ~3-minute poll interval, or click Refresh to force it.
  • Click into the app: the resource tree — Deployment → ReplicaSet → Pod — with the new Pod replacing the old one.
  • Terminal: the running pod's image, confirming the new tag actually landed.
terminal — open the ArgoCD UI

kubectl -n argocd port-forward svc/argocd-server 8080:443
# open https://localhost:8080 — admin / (see: kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d)
terminal — confirm the new image is actually running

kubectl get pods -n flag-service -o jsonpath='{.items[0].spec.containers[0].image}'
Say
  • "ArgoCD is watching gitops/flag-service in this repo continuously. That bot commit from Segment 5 is a change in the source of truth, so it detects drift, and because auto-sync and self-heal are both on, it applies it without anyone touching kubectl."
  • "This closes the loop end to end — a code change became a running pod through nothing but git commits."
