01

Introdução

0:30
Falar
  • "Este é o ToggleMaster, uma plataforma de feature flags construída como 5 microsserviços — auth, flag, targeting, evaluation, analytics — para o Tech Challenge Fase 3 da POSTECH."
  • "A Fase 2 validou a arquitetura, mas tudo foi criado manualmente: kubectl apply na mão, credenciais em texto puro, sem pipeline. Esta fase substitui tudo isso por Terraform, pipelines de DevSecOps no GitHub Actions, e GitOps via ArgoCD."
  • "Vou mostrar quatro coisas: a infraestrutura como código, um pipeline realmente bloqueando uma vulnerabilidade crítica e depois passando após a correção, o GitOps atualizando o deployment automaticamente, e o ArgoCD sincronizando essa mudança no cluster sem nenhum passo manual."
02

Infraestrutura como Código

3:30
Mostrar
  • A estrutura da pasta terraform/ — configuração raiz + modules/ (networking, eks, rds, elasticache, dynamodb, sqs, ecr, irsa, github-oidc).
  • O terraform plan rodando contra o estado real.
  • Console da AWS: VPC → cluster EKS togglemaster → as 3 instâncias RDS → ElastiCache → tabela DynamoDB → fila SQS → os 5 repositórios ECR.
terminal

cd terraform
terraform plan
O objetivo deste momento: o plan reporta 0 to add, 0 to change, 0 to destroy — a prova de que todo o ambiente AWS na tela foi produzido por este código, não por cliques no console, e que nada mudou desde então.
Falar
  • "Cada módulo é separado e reutilizável — networking, EKS, e um único módulo de RDS instanciado três vezes via for_each para os três bancos Postgres."
  • "O state não é local — é um backend S3 versionado e criptografado, com lock nativo, provisionado por uma configuração de bootstrap separada, então seu ciclo de vida é desacoplado do ambiente que ele armazena."
  • "Esta é uma conta pessoal da AWS, então o Terraform cria suas próprias IAM roles — a role do cluster EKS, a role dos nodes, e duas roles de IRSA que permitem que o evaluation-service e o analytics-service acessem o SQS e o DynamoDB sem nenhuma chave AWS estática em lugar nenhum."
  • "O terraform plan reportando zero mudanças é a prova real de que isso corresponde ao que está no ar — é tudo isso que vocês vão ver no console a seguir."
03

Anatomia do pipeline

1:30
Mostrar
  • Abrir o .github/workflows/flag-service-ci.yml no GitHub, e o grafo de jobs de uma execução anterior bem-sucedida na aba Actions.
✓ Build & Unit Test ✓ Linter ✓ Security Scan ✓ Docker Build & Push ✓ Update GitOps manifest
Falar
  • "Cinco jobs, em todo push na main e todo pull request: build & unit test, lint, um security scan, build e push da imagem Docker, e uma atualização do GitOps — os dois últimos só rodam em push na main, não em PRs."
  • "O security scan faz duas coisas — SCA com o Trivy contra o manifesto de dependências, e SAST com gosec ou bandit dependendo da linguagem. Se qualquer um deles encontrar algo CRÍTICO, o pipeline para antes mesmo de construir a imagem."
  • "O push para o ECR usa o token OIDC do GitHub para assumir uma role da AWS diretamente — nenhuma access key parada em um secret do GitHub."
04

DevSecOps: falhar, depois corrigir

4:30 o momento obrigatório
Mostrar
  • Editor: abrir o flag-service/requirements.txt, adicionar uma linha, salvar.
  • Terminal: commit e push.
  • GitHub Actions: o job security-scan ficando vermelho, com a tabela do Trivy visível no log.
flag-service/requirements.txt — adicionar esta linha

PyYAML==5.3
terminal

git add flag-service/requirements.txt
git commit -m "test: adicionar dependência vulnerável"
git push
O que o Trivy realmente reporta — verificado localmente antes da gravação, então isso é garantido reproduzir na câmera:
BibliotecaCVESeveridadeCorrigido emProblema
PyYAMLCVE-2020-14343CRITICAL5.4correção incompleta da CVE-2020-1747
PyYAMLCVE-2020-1747CRITICAL5.3.1execução arbitrária de comandos via FullLoader
Falar (enquanto está vermelho)
  • "Estou adicionando uma versão de pacote real e conhecidamente vulnerável — o PyYAML 5.3 tem duas CVEs CRÍTICAS de execução arbitrária de código. Ele nem é importado em nenhum lugar do código; o Trivy escaneia o próprio manifesto de dependências, que é exatamente o objetivo do SCA."
  • "O pipeline falha bem aqui, no security-scan — nunca chega no build Docker, nunca chega no ECR, nunca chega no cluster. Essa é a regra de bloqueio que o desafio pede."
Mostrar
  • Editor: apagar a linha PyYAML==5.3, salvar.
  • Terminal: commit e push de novo.
  • GitHub Actions: o mesmo job ficando verde.
terminal

git add flag-service/requirements.txt
git commit -m "fix: remover dependência vulnerável"
git push
Falar (enquanto está verde)
  • "Mesmo formato de commit, uma linha removida — o security-scan passa, e agora a cadeia inteira roda: build Docker, scan da imagem do container, push para o ECR, e o job de atualização do GitOps. Deixa rodando — isso é o Segmento 5."
05

GitOps: a atualização da tag

3:30
Mostrar
  • GitHub Actions: o log do job update-gitops — o passo do sed, depois o passo de commit/push.
  • GitHub: o histórico de commits do repositório — um novo commit criado pelo github-actions[bot].
  • O diff em gitops/flag-service/deployment.yaml: a tag da linha image: mudando para o novo hash do commit.
terminal — depois do push, quando o CI terminar

git log --oneline -5 -- gitops/flag-service/deployment.yaml
git pull
git diff HEAD~1 -- gitops/flag-service/deployment.yaml
Falar
  • "O CI nunca roda kubectl apply. O último job dele edita exatamente uma linha — a tag da imagem — em gitops/flag-service/deployment.yaml, e faz commit dessa mudança de volta neste mesmo repositório usando o próprio token do workflow."
  • "Esse commit é toda a interface entre CI e CD. Nada depois disso precisa de acesso do pipeline ao cluster."
06

ArgoCD: a sincronização

3:30
Mostrar
  • A interface do ArgoCD: o card do flag-service mudando de Synced para OutOfSync para Syncing e voltando para Synced — normalmente dentro do intervalo de ~3 minutos de verificação automática, ou clique em Refresh para forçar.
  • Clicar na aplicação: a árvore de recursos — Deployment → ReplicaSet → Pod — com o novo Pod substituindo o antigo.
  • Terminal: a imagem do pod rodando, confirmando que a nova tag realmente chegou.
terminal — abrir a interface do ArgoCD

kubectl -n argocd port-forward svc/argocd-server 8080:443
# abrir https://localhost:8080 — admin / (ver: kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d)
terminal — confirmar que a nova imagem está realmente rodando

kubectl get pods -n flag-service -o jsonpath='{.items[0].spec.containers[0].image}'
Falar
  • "O ArgoCD está observando gitops/flag-service neste repositório continuamente. Aquele commit do bot do Segmento 5 é uma mudança na fonte de verdade, então ele detecta o desvio, e como auto-sync e self-heal estão ligados, ele aplica sem ninguém tocar no kubectl."
  • "Isso fecha o ciclo de ponta a ponta — uma mudança de código virou um pod rodando através de nada além de commits do git."
